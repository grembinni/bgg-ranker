# Phase 03.1: Code Review Report

**Reviewed:** 2026-05-25
**Depth:** standard
**Files Reviewed:** 6
**Status:** issues_found

## Summary

This phase repairs the BGG sync write path across three areas: (1) a Vite proxy X-BGG-Session header fallback to construct a Cookie when `proxySession` is null; (2) `ajax=1` in the `bggRateGame` POST body with structured error logging; and (3) replacement of the blunt `syncedGameIds` accumulator with per-game `dirtyGameIds` tracking. The implementation is largely correct and the dirty-tracking design is sound. Two correctness defects were found: one latent type-safety gap in `startSync` that would send `rating=NaN` to BGG under a currently unreachable but unguarded condition, and an unsanitized header-injection vector in the dev proxy fallback. Three warnings cover behavioral issues — a skip-queue drain bug in `pick()` that was present before this phase but is unrelated to dirty tracking, and two minor sync-loop issues.

## Critical Issues

### CR-01: `startSync` sends `rating=NaN` to BGG when a dirty game ID is absent from both `ratings` and `unplayedIds`

**File:** `src/store/store.ts:461`

**Issue:** `get().ratings[gameId]` has TypeScript type `number` (because `noUncheckedIndexedAccess` is not enabled in `tsconfig.app.json`) but returns `undefined` at runtime when `gameId` is not a key of `ratings`. If any game ends up in `dirtyGameIds` without a matching entry in `ratings` or `unplayedIds` — which current code paths do not produce, but the guard is entirely absent — `ratingInt` is `undefined`, `undefined / 100` is `NaN`, `NaN.toFixed(2)` is `'NaN'`, and `bggRateGame` POSTs `rating=NaN` to BGG. BGG's behavior on receiving `rating=NaN` is undocumented and could silently corrupt a game's rating.

The condition is currently unreachable because every mutation that populates `dirtyGameIds` also puts the game in either `ratings` (pick, reorderRankedList, moveUnplayedToRanked, refresh, fetchCollection) or `unplayedIds` (markUnplayed), and `resetForNewUser` clears both. However there is no runtime assertion or type narrowing enforcing this invariant, so a future code change could silently introduce the bug.

**Fix:** Add a defensive undefined check and skip (or abort) the game rather than sending garbage to BGG:

```typescript
// src/store/store.ts — inside startSync for-loop, replacing line 461
const isUnplayed = get().unplayedIds.includes(gameId)
const ratingInt = isUnplayed ? null : get().ratings[gameId]
// Guard against state inconsistency — dirtyGameIds entry with no rating and not unplayed
if (!isUnplayed && ratingInt === undefined) {
  get().markGameSynced(gameId) // drop from dirty set; skip BGG write
  continue
}
```

Alternatively, enable `"noUncheckedIndexedAccess": true` in `tsconfig.app.json` to make TypeScript surface this class of error project-wide (the return type of `ratings[gameId]` becomes `number | undefined`, forcing explicit handling).

### CR-02: Proxy X-BGG-Session fallback constructs Cookie without sanitizing the header value

**File:** `vite.config.ts:33`

**Issue:** The `xBggSession` value is read directly from `req.headers['x-bgg-session']` and interpolated without validation into the outgoing Cookie header:

```typescript
const session = proxySession ?? devSession ?? (xBggSession ? `SessionID=${xBggSession}` : null)
if (session) proxyReq.setHeader('Cookie', session)
```

HTTP header values are not sanitized. A session ID containing semicolons, whitespace, or CRLF sequences (e.g., `abc; Domain=.attacker.com` or `abc\r\nX-Injected: value`) would produce a malformed or injected Cookie header sent upstream to BGG. While this path is dev-only (Vite proxy) and a session ID value of attacker-controlled length is unlikely in normal operation, the design assumes the client is trusted, which conflicts with the proxy's purpose of mediating untrusted input.

**Fix:** Validate the header value before use. Session IDs from BGG's login response are alphanumeric hex strings. Reject anything that contains characters outside that set:

```typescript
const xBggSessionRaw = req.headers['x-bgg-session'] as string | undefined
proxyReq.removeHeader('x-bgg-session')
// Sanitize: BGG session IDs are hex strings; reject any value containing unsafe chars
const xBggSession =
  xBggSessionRaw && /^[A-Za-z0-9_-]+$/.test(xBggSessionRaw) ? xBggSessionRaw : undefined
const session = proxySession ?? devSession ?? (xBggSession ? `SessionID=${xBggSession}` : null)
if (session) proxyReq.setHeader('Cookie', session)
```

## Warnings

### WR-01: `pick()` passes pre-drain `skipQueue` to `selectRandomPair`, causing the current skipped pair to be served again as next comparison

**File:** `src/store/store.ts:338-341`

**Issue:** `newQueue` (the drained skip queue) is computed correctly at line 338, but `nextPair` is computed at line 341 using the **original** (undrained) `skipQueue`:

```typescript
const newQueue = skipQueue.length > 0 ? skipQueue.slice(1) : skipQueue  // line 338 — correct drain
const nextPair = selectRandomPair(newRatings, skipQueue)                  // line 341 — WRONG: uses undrained queue
```

`selectRandomPair` returns `skipQueue[0]` when the queue is non-empty. If the current pair being picked was itself `skipQueue[0]` (i.e., it was a re-presentation of a previously skipped game pair), then `nextPair` equals `skipQueue[0]` — the same pair just picked. The user briefly sees the same matchup again before the state update completes. The stored `skipQueue` is correctly drained to `newQueue`, but `currentPair` is set to the pair that was just removed from the queue.

This was present before this phase and is not a dirty-tracking regression, but it should be fixed. The fix is one word:

```typescript
// Replace line 341:
const nextPair = selectRandomPair(newRatings, newQueue)  // use drained queue
```

### WR-02: `delay(1000)` fires unconditionally after the last write, adding a 1-second stall before sync completes

**File:** `src/store/store.ts:479-480`

**Issue:** The throttle delay at line 480 is placed at the end of the `for` loop body unconditionally. After the last game in `toSync` is successfully written, the loop waits 1000ms before falling through to `completeSyncAll()`. A user syncing a single dirty game sees "Syncing…" for a full second after the write has already succeeded. For a 10-game sync the total unnecessary wait is 1 second (the post-last-write delay) on top of the 9 inter-write delays.

**Fix:** Apply the delay only between writes, not after the last one:

```typescript
for (let i = 0; i < toSync.length; i++) {
  const gameId = toSync[i]
  // ... existing per-game logic ...
  // Only delay between writes, not after the last one
  if (i < toSync.length - 1) {
    await delay(1000)
  }
}
```

### WR-03: `reAuthAndResume` calls `startSync()` without checking that `dirtyGameIds` is still non-empty

**File:** `src/store/store.ts:507-521`

**Issue:** After re-authentication, `reAuthAndResume` calls `get().startSync()` unconditionally (line 519). If all games happened to be synced between the session expiry and the re-auth (e.g., the user made no additional picks but another tab somehow modified state), `startSync` runs with an empty `dirtyGameIds`, transitions to `view: 'syncing'` with `syncTotal: 0`, completes the zero-iteration loop, and calls `completeSyncAll()`. The user sees a flash of the syncing view with a 0/0 counter before being returned to comparison view after the 2-second delay.

This is a minor issue because `dirtyGameIds` emptying spontaneously between a session expiry and re-auth is effectively impossible in the single-tab SPA model. But the guard is cheap and eliminates the ghost cycle:

```typescript
async reAuthAndResume(password: string): Promise<void> {
  // ...
  set({ sessionId: result.sessionId, syncStatus: 'idle' })
  if (get().dirtyGameIds.length === 0) {
    set({ view: 'comparison' })
    return
  }
  await get().startSync()
}
```
