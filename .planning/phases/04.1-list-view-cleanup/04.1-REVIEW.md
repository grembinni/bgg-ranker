## Warnings

### WR-01: RankedGridView displays "Rankings 1–0 of N" when ratings is empty

**File:** `src/components/RankedGridView.tsx:141`  
**Issue:** The pagination label is computed as `Rankings {safeOffset + 1}–{Math.min(safeOffset + 100, orderedIds.length)} of {orderedIds.length}`. When `orderedIds.length === 0` (user's entire collection is unrated), this produces `Rankings 1–0 of 0`, which is nonsensical and will confuse users. This state is reachable: `fetchCollection` places all games with `userRating === null` into `unplayedIds` and calls `initializeRankings([])`, which returns `{}`. The view then transitions to `'comparison'`, from which `showRankedGrid()` is accessible.

**Fix:**
```tsx
<span className="text-sm text-gray-600">
  {orderedIds.length === 0
    ? 'No ranked games'
    : `Rankings ${safeOffset + 1}–${Math.min(safeOffset + 100, orderedIds.length)} of ${orderedIds.length}`}
</span>
```

### WR-02: ComparisonView hamburger menu has no click-outside-to-close handler

**File:** `src/components/ComparisonView.tsx:54–79`  
**Issue:** `menuOpen` is set to `true` when the hamburger button is clicked, but there is no `document` click handler or `onBlur` to dismiss the menu when the user clicks anywhere outside it. The three action buttons each call `setMenuOpen(false)` before acting, and clicking the hamburger icon again toggles it closed. However, clicking anywhere else on the page — including the two game cards, the Skip/Grid/Unplayed buttons — leaves the menu open. This is a usability defect: the open menu obscures the top-left of the UI with no obvious escape path.

**Fix:** Add a `useEffect` that registers a `mousedown` capture listener while `menuOpen` is true, and closes the menu when a click outside the menu div is detected. A simpler alternative is a backdrop overlay:
```tsx
{menuOpen && (
  <>
    <div
      className="fixed inset-0 z-10"
      onClick={() => setMenuOpen(false)}
    />
    <div className="absolute left-0 top-full mt-1 w-44 bg-white border border-gray-200 rounded shadow-sm z-20 flex flex-col">
      {/* ...menu items... */}
    </div>
  </>
)}
```

### WR-03: Module-level timer variables are shared across all store instances

**File:** `src/store/store.ts:120–121`  
**Issue:** `completeSyncTimer` and `upsetTimer` are declared at module scope rather than per-store-instance scope:
```ts
let completeSyncTimer: ReturnType<typeof setTimeout> | null = null
let upsetTimer: ReturnType<typeof setTimeout> | null = null
```
`createAppStore` is exported and called both in production (once, for `useStore`) and in every test that calls `createAppStore(createMockStorage())`. When two store instances have timers running simultaneously — which happens in tests that call `completeSyncAll()` or `pick()` with an upset — a timer set by one instance can be cleared by another. In the `startSync throttle` test (line 665), `vi.useFakeTimers()` is used and the 2000 ms timer is drained; but the `completeSyncAll` tests at lines 717–755 call `completeSyncAll()` without draining the timer, leaving a real (non-fake) `setTimeout` running in the module. If a subsequent test calls `completeSyncAll()` on a different store, the previous timer is cleared on line 495, potentially masking side-effects.

**Fix:** Move the timer variables inside `createAppStore` as closed-over local variables:
```ts
export function createAppStore(rawStorage: StateStorage) {
  let completeSyncTimer: ReturnType<typeof setTimeout> | null = null
  let upsetTimer: ReturnType<typeof setTimeout> | null = null
  // ...rest of function
}
```
This gives each store instance its own independent timer handles and prevents cross-instance interference.

### IN-01: login() auto-resume path leaves stale loadingMessage in state

**File:** `src/store/store.ts:395–419`  
**Issue:** The `login()` action sets `loadingMessage: 'Logging in to BGG…'` at line 396, then on the happy-path auto-resume (lines 400–408) calls `continueSession()` and returns without clearing `loadingMessage`. After auto-resume, state has `view: 'comparison'` but `loadingMessage: 'Logging in to BGG…'`. `CollectionLoading` is the only component that reads `loadingMessage` and it is unmounted when `view !== 'loading'`, so the stale string is not displayed. The inconsistency is harmless today but could silently surface in a future `CollectionLoading` refactor.

**Fix:**
```ts
if (...auto-resume condition...) {
  set({ loadingMessage: null })
  get().continueSession()
  return
}
```

### IN-02: Test mock data repeatedly omits required `collId` field

**File:** `src/store/store.test.ts:137–140, 222–225, 535–537, 563–566`  
**Issue:** Multiple `vi.mocked(mockBggFetch).mockResolvedValueOnce([...])` calls supply game objects without a `collId` property, violating the `RawGame` type contract. Because all these games have `userRating: null` they land in `unplayedIds` rather than `ratings`, so the missing field does not affect the assertions being tested. TypeScript does not flag this because `mockResolvedValueOnce` does not enforce the resolved-type shape at the call site. If any of these test paths were extended to exercise sync (which requires `collId`), the tests would silently exercise a broken code path.

**Fix:** Add `collId` to every mock game object. For example:
```ts
{ id: 'g0', collId: 'c0', name: 'Game 0', yearPublished: 2020, thumbnail: '', userRating: null }
```

### IN-03: preloadedUrls Set in RankedGridView grows without bound

**File:** `src/components/RankedGridView.tsx:67, 95–101`  
**Issue:** `preloadedUrls` is a `useRef<Set<string>>` that accumulates every thumbnail URL that has been passed to `preloadImages()`. It is never cleared within the component's lifetime. For a collection near the 990-game ceiling, after enough page navigation the `Set` will hold close to 990 URL strings — a minor memory overhead. More practically, the `Set` is checked to avoid re-creating `Image` objects, which is the correct intent. No functional bug, just a maintenance note.

**Fix:** No action required for typical collection sizes. If memory budget becomes a concern, cap the Set or use a `WeakRef` map. Alternatively, the browser's own HTTP cache already deduplicates image fetches, so the `Set` guard is unnecessary and can be removed entirely.
