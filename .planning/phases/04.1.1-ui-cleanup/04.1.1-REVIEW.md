# Phase 04.1.1: Code Review Report

**Reviewed:** 2026-07-17T00:00:00Z
**Depth:** standard
**Files Reviewed:** 10
**Status:** issues_found

## Summary

This phase consolidated per-view headers (previously duplicated in `ComparisonView`, `RankedGridView`, `RankedListView`, `UnplayedListView`) into a single global `Header.tsx`, changed the default landing view from `comparison` to `ranked-grid` in the store, and cleaned up navigation. The refactor itself is clean — dead imports were removed correctly and the test suites for `Header` and `ComparisonView` are thorough.

Two issues rise to BLOCKER: a pre-existing (not introduced this phase, but present in a reviewed file) data-integrity bug in `startSync()` where failed BGG writes get silently recorded as "synced," and a newly-introduced layout defect where `RankedGridView`'s pagination click-zones can visually and functionally occlude the new global `Header`'s hamburger menu button on common viewport widths. Several warnings and info-level issues are also documented below, including a module-level timer-sharing bug in the store that risks cross-instance test contamination, and a duplicate-icon usability issue introduced by the new `Header`.

## Critical Issues

### CR-01: Failed BGG sync writes are silently recorded as successfully synced, permanently masking the divergence

**File:** `src/store/store.ts:494-511` (catch block), interacting with `src/store/store.ts:528-535` (`completeSyncAll`) and `src/store/store.ts:241-248` (`fetchCollection` dirty-detection)

**Issue:**
In `startSync()`, when `bggRateGame()` throws a **non-401** error (network failure, HTTP 5xx, etc.), the catch block records the game name in `syncSkippedGames` for a one-time toast, but then unconditionally calls `get().markGameSynced(gameId)`:

```ts
} catch (err) {
  const status = (err as { status?: number }).status
  if (status === 401) {
    set({ syncStatus: 'session-expired' })
    return
  }
  ...
  set({ syncSkippedGames: [...get().syncSkippedGames, gameName] })
  get().markGameSynced(gameId)   // <-- removes gameId from dirtyGameIds despite the write NEVER reaching BGG
  if (i < syncQueue.length - 1) await delay(500)
  continue
}
```

`markGameSynced()` removes the game from `dirtyGameIds`. Because the local `ratings[gameId]` was never rolled back (the failure is in the network write, not the local computation), `completeSyncAll()` then snapshots **all** current ratings — including the one that failed to write — into `lastSyncedRatings`:

```ts
completeSyncAll(): void {
  ...
  set({
    ...
    lastSyncedRatings: { ...get().ratings },   // includes the never-persisted rating
    ...
  })
}
```

On the next `fetchCollection()` (login, refresh, or app reload), the dirty-detection filter treats this game as already reconciled because `lastSynced[g.id] === newRating` short-circuits before comparing to BGG's actual stored rating:

```ts
const dirtyGameIds = ratedGames
  .filter(g => {
    const newRating = ratings[g.id]
    if (lastSynced[g.id] === newRating) return false   // masks the failed write
    return newRating !== Math.round((g.userRating as number) * 100)
  })
```

The net effect: a game whose rating write to BGG failed is permanently treated by the app as in-sync with BGG, even though BGG's server-side rating never changed. The user has no way to discover or retry this — the one-time `syncSkippedGames` toast is the only signal, and it disappears without leaving the game "dirty" for a future sync attempt. This is a silent, permanent data-integrity divergence between the local ranking and the user's actual BGG collection ratings — the exact class of bug the project's `bggRateGame()` isolation and dirty-tracking design is meant to prevent.

**Fix:** Do not call `markGameSynced()` (or write the failed game's rating into `lastSyncedRatings`) on a genuine write failure. Keep the game in `dirtyGameIds` so a subsequent sync retries it, and only add it to `syncSkippedGames` for display:

```ts
} catch (err) {
  const status = (err as { status?: number }).status
  if (status === 401) {
    set({ syncStatus: 'session-expired' })
    return
  }
  const body = (err as { body?: string }).body
  const detail = `${status ? `HTTP ${status}` : 'network error'}${body ? ` — ${body}` : ''}`
  console.error(`[startSync] skipping ${gameId}: ${detail}`)
  const gameName = get().games[gameId]?.name ?? gameId
  // Only advance progress display — do NOT clear dirtyGameIds or count this as synced.
  set({
    syncSkippedGames: [...get().syncSkippedGames, gameName],
    syncProgress: get().syncProgress + 1,
  })
  if (i < syncQueue.length - 1) await delay(500)
  continue
}
```
And ensure `completeSyncAll()`'s `lastSyncedRatings` snapshot excludes games still present in `dirtyGameIds` (or is built from only the games actually written this run) so the next `fetchCollection()` correctly re-flags them as dirty.

### CR-02: Ranked-grid pagination click-zones can cover and block the Header's hamburger menu button

**File:** `src/components/RankedGridView.tsx:142-157` (click zones), interacting with `src/components/Header.tsx:30-41` (hamburger button)

**Issue:**
When paginated past the first page (`safeOffset > 0`), `RankedGridView` renders a full-height, viewport-fixed click zone for "previous page":

```tsx
{safeOffset > 0 && (
  <div
    className="fixed left-0 top-0 bottom-0 w-24 cursor-pointer z-10 flex items-center justify-center group"
    onClick={() => setPageOffset(Math.max(0, safeOffset - 100))}
  >
    <span className="text-5xl text-gray-300 group-hover:text-gray-500 select-none">‹</span>
  </div>
)}
```

This is `position: fixed` with an explicit `z-index` (`z-10`), so per CSS stacking rules it paints above any non-positioned (`position: static`) content on the page **regardless of DOM order** — including the global `Header`, whose outer container (`<div className="max-w-6xl mx-auto px-4 pt-8">`, `Header.tsx:31`) has no `position`/`z-index` of its own.

The Header's hamburger button sits `justify-self-start` inside that `max-w-6xl` (1152px) centered container with `px-4` (16px) padding. At common viewport widths (~1152px–1344px, i.e. most 13"–15" laptop displays), the hamburger button's screen position falls within the leftmost 96px (`w-24`) of the viewport — exactly where the fixed click-zone is rendered, at `top-0 bottom-0` (full page height, so it also covers the header row, not just the grid body).

Net effect: on these common viewport widths, once the user pages past screen 1 of the ranked grid, the click-zone silently intercepts clicks intended for the hamburger menu button, making Sync/Refresh/Unplayed/Logout (all only reachable via that menu) unreachable until the user pages back to the first screen.

**Fix:** Scope the click-zones to the grid body only (not full viewport height), or give the `Header` a higher stacking context so it always paints above pagination click-zones, e.g.:

```tsx
// Header.tsx — elevate above page-level fixed overlays
<div className="relative z-30 max-w-6xl mx-auto px-4 pt-8">
```
or constrain the click-zone's vertical extent to below the header:
```tsx
<div
  className="fixed left-0 top-24 bottom-0 w-24 cursor-pointer z-10 ..."
  ...
/>
```

## Warnings

### WR-01: Module-level sync/upset timers are shared across all `createAppStore()` instances

**File:** `src/store/store.ts:151-152`

**Issue:**
```ts
let completeSyncTimer: ReturnType<typeof setTimeout> | null = null
let upsetTimer: ReturnType<typeof setTimeout> | null = null
```
These are declared at module scope, outside `createAppStore()`, so every store instance created by calling `createAppStore()` shares the *same* timer variables. In production only one instance exists (`export const useStore = createAppStore(_lazyStorage)`), so runtime impact is limited today — but `store.test.ts` creates dozens of independent store instances via `createAppStore(createMockStorage())`, several of which trigger `pick()`-driven upset timers or sync-completion timers using real timers (no `vi.useFakeTimers()`). Because the timer variable is shared, a pending real timer from an earlier test's store instance can be silently cancelled and replaced by a later test's `pick()`/`completeSyncAll()` call (the code's own `if (upsetTimer) clearTimeout(...)` guard fires against the *wrong* store's timer), or a timer can fire after its originating test has finished, invoking `set()` on a store instance whose test context has already been torn down. This is a latent source of test flakiness and, if `createAppStore()` is ever called more than once at runtime (e.g. during Vite HMR, multi-tab/testing scenarios, or a future refactor), a real bug where one store's sync/upset lifecycle bleeds into another's.

**Fix:** Move both timer variables inside `createAppStore()` so each store instance owns independent timer state:
```ts
export function createAppStore(rawStorage: StateStorage) {
  const storage = createJSONStorage(() => rawStorage)
  let completeSyncTimer: ReturnType<typeof setTimeout> | null = null
  let upsetTimer: ReturnType<typeof setTimeout> | null = null
  return create<AppStore>()(
    persist(
      (set, get) => ({ ... }),
      { ... }
    )
  )
}
```

### WR-02: Games skipped due to missing rating or `collId` during sync are never marked synced, never reported, and remain silently stuck dirty forever

**File:** `src/store/store.ts:490-493`

**Issue:**
```ts
const ratingInt = get().unplayedIds.includes(gameId) ? null : get().ratings[gameId]
if (ratingInt === undefined) continue
const game = get().games[gameId]
if (!game?.collId) continue
```
Unlike the network-failure catch block (which at least appends to `syncSkippedGames` for a one-time user-visible toast), these two `continue` paths give **no feedback at all**: the game is neither marked synced (so it correctly stays in `dirtyGameIds`) nor reported to the user, and `syncProgress` is never incremented for it, so the progress indicator will never reach `syncTotal` when this path is hit. The user has no visibility into why a game keeps failing to sync run after run.

**Fix:** Route these paths through the same `syncSkippedGames` reporting as network failures (without calling `markGameSynced`, so they correctly remain retryable):
```ts
if (ratingInt === undefined) {
  set({ syncSkippedGames: [...get().syncSkippedGames, get().games[gameId]?.name ?? gameId] })
  continue
}
```

### WR-03: Header's hamburger "Menu" button and the "Ranked list view" button use the identical glyph

**File:** `src/components/Header.tsx:40`, `src/components/Header.tsx:91`

**Issue:** Both buttons render the literal `☰` character:
```tsx
<button ... aria-label="Menu">☰</button>
...
<button ... aria-label="Ranked list view">☰</button>
```
Screen readers distinguish them via `aria-label`, but sighted users see two visually identical icons performing different actions (opening a dropdown menu vs. switching to the ranked-list view) in the same header row. This is a usability regression introduced by this phase's header consolidation (the previous `ComparisonView` menu button also used `☰`, but there was no second `☰` icon competing for attention in the same row).

**Fix:** Use a distinct hamburger glyph for the menu trigger (e.g. `⋮` / `≡` / a dedicated icon component) so it's visually distinguishable from the ranked-list view-switch icon.

### WR-04: UnplayedListView "Add" button is not disabled for out-of-range input, and silently no-ops on invalid values

**File:** `src/components/UnplayedListView.tsx:17-21`, `src/components/UnplayedListView.tsx:41-48`

**Issue:**
```ts
function handleAdd() {
  const val = parseInt(rankInput, 10)
  if (isNaN(val) || val < 1 || val > max) return
  onMove(id, val)
}
```
```tsx
<button
  type="button"
  onClick={handleAdd}
  disabled={rankInput === ''}
  ...
>
  Add
</button>
```
The button is only disabled when the field is empty. If the user types a value outside `1..max` (e.g. `999`, `0`, or non-numeric text that still parses partially), the button remains enabled and clickable, but `handleAdd()` silently returns without moving the game and without any error message — the user gets no feedback that their input was rejected.

**Fix:** Either disable the button for out-of-range values, or show inline validation feedback:
```ts
const val = parseInt(rankInput, 10)
const isValid = !isNaN(val) && val >= 1 && val <= max
...
<button disabled={!isValid} ...>Add</button>
```

## Info

### IN-01: `version` field is persisted but never read — dead/inert schema-versioning mechanism

**File:** `src/store/store.ts:168` (initial state), `src/store/store.ts:588` (partialize)

**Issue:** `state.version` is initialized to `1` and included in the persisted payload (`partialize`), but no code anywhere reads `state.version` or `parsed.state.version` to gate a migration or discard stale data. The actual protection described in `CLAUDE.md` ("localStorage key format: `bgg-ranker:v1:<slice>` … versioned to prevent stale schema corruption") is provided entirely by the storage *key name* (`bgg-ranker:v1:collection-and-rankings`), not by this field. As written, `version` is dead weight that could mislead a future maintainer into believing it drives migration logic.

**Fix:** Either wire `version` into zustand's `persist` `version`/`migrate` options, or remove the field and rely solely on the key-name versioning scheme (documenting that choice).

### IN-02: Broken thumbnail images in the ranked grid leave a blank, unstyled cell

**File:** `src/components/RankedGridView.tsx:45-54`

**Issue:**
```tsx
{thumbnail ? (
  <img
    src={normalizeUrl(thumbnail)}
    alt=""
    className="w-full h-full object-cover"
    onError={(e) => { (e.target as HTMLImageElement).style.display = 'none' }}
  />
) : (
  <div className="w-full h-full bg-gray-100" />
)}
```
When an `<img>` fails to load (broken URL, network error), `onError` hides it via `display: none`, but there is no fallback background/placeholder applied to the wrapping cell — unlike the "no thumbnail" branch, which shows a `bg-gray-100` placeholder. The result is a blank/transparent square in the grid with no visual indication a game exists there.

**Fix:** On error, swap to the same placeholder styling used for the no-thumbnail case (e.g. toggle a small `broken` state per cell) rather than just hiding the image.

### IN-03: RankedListView and UnplayedListView no longer show any total/count indicator after per-view headers were removed

**File:** `src/components/RankedListView.tsx`, `src/components/UnplayedListView.tsx`

**Issue:** Prior to this phase, each view had its own header showing a count (`Rankings (N games)`, `Unplayed (N games)`). This phase removed those headers entirely in favor of the global `Header`, but the global `Header`'s hamburger dropdown only surfaces the unplayed count (`Unplayed ({unplayedIds.length})`) — the ranked-list total is not shown anywhere while on the `RankedListView` screen (contrast with `RankedGridView`, which still shows `Rankings {from}–{to} of {total}` in its pagination bar). This is likely an intentional simplification, but it is a net loss of at-a-glance information on the list view specifically.

**Fix:** Consider surfacing the total ranked count somewhere on `RankedListView` (e.g. a small caption above the list), consistent with `RankedGridView`.

### IN-04: Header dropdown menu has no keyboard/touch-friendly dismissal

**File:** `src/components/Header.tsx:33-34`

**Issue:** The dropdown only opens/closes via click-toggle on the hamburger button or a 150ms `onMouseLeave` timer on the wrapping container. There's no `Escape` key handling and no document-level "click outside" listener. Keyboard users who tab into the menu have no way to close it except tabbing back to the hamburger button and pressing it again (toggling it closed), and on touch devices (no `mouseleave`), only the toggle-button-again path works. This is a minor accessibility/robustness gap for a newly-introduced interactive component.

**Fix:** Add an `Escape` keydown handler and/or a document click-outside listener to close the menu, in addition to the existing hover-based dismissal.
